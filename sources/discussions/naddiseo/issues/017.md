## 1. Independent re-verification of chain 2

The trailing blob on the phase-3.2 page (salt `b45a5e3d`) decrypts with `WIF(K_C1)` (EVP-MD5, AES-256-CBC) into a clean 79-byte payload:

```
K_S1 = b06fa6f20561756c865dac7190f063480a371e4a13206e529ee7e9078f309c4b
K_S2 = b11d211ca0a17cd68c580308f3e6f21d3f935c8da3c4373b6f73ab5ccfaea597
E_S  = 740a25de4b8e946d0a5ae2667a23a2
```

`E_S` matches the documented value exactly, and the PKCS7 padding is valid, so this link (chain1 -> WIF(K_C1) -> chain2) is solid, not a false positive.

## 2. The natural continuation fails on the cosmic blob

If each blob's password were WIF(K1 of the previous payload), the cosmic blob (salt `2d3f6fe0`) should open with `WIF(K_S1)`. It does not. I tested:

- WIF(K_S1), WIF(K_S2), compressed WIFs of both, uppercase/lowercase
- WIF(K_C2) (the other chain1 key), compressed and uncompressed
- raw/hex of K_S1/K_S2/E_C/E_S, `E_C||E_S`, sha256 variants
- EVP-MD5, EVP-SHA1, EVP-SHA256 and PBKDF2, AES-CBC and AES-CFB

All fail (no valid padding, no readable output). So either the chain pattern changes at the cosmic blob (the way the unverified fork's chain4 password `E_C||E_S||E_B[:2]` departs from the WIF pattern), or the cosmic blob's password comes from somewhere else entirely.

## 4. The actual question

@Naddiseo you have said that a true cosmic decryption should be "plain text readable English". Two questions:

1. Is that expectation something the creator communicated to you directly (or that you saw in material not in the repo), or is it an inference from how every other blob in the puzzle behaves?
2. Is there any indication anywhere of where the cosmic blob's password is supposed to come from? The creator's 2023-02-23 message lists `yellow blue primes matrixsumlist lastwordsbeforearchichoice yinyang` and says the password is "in front of your eyes". I've tested that ingredient list in the phase-3 style (sha256 of concatenated resolutions, all orderings and many value assignments, ~2,400 candidates) and lexically, plus sha256 readings of the remaining board tokens (`shabef anstoo` = sha256 + operand, etc.), with no hit.

For context on the two undecoded streams (DBBI 91, FAED 570): the digit stream contains no zero at all (which for the z-section trick, hex->decimal, would force a plaintext with no p/P/spaces/0), the letter arrangement passes uniform-random tests on pairs/triplets, and saama143's a/b/c expansion to 13x13 and 35x35 reads as noise under row/column/serpentine/spiral orderings with base-3 interpretations. So if there is something known about the *kind* of thing those two blocks are (checksum, filler, key material rather than text), that would narrow the search space a lot.
